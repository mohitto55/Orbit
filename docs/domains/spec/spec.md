# Spec 기능 명세

도메인마다 기능 명세 표를 두고, 기능별 요구사항과 수용 기준(AC)을 관리한다. (2층)

| ID | 기능 | 목적 | 수용 기준 | 상태 |
|---|---|---|---|---|
| SP-F01 | 기능 명세 표 만들기 | 도메인의 요구사항을 한눈에 본다 | AC1: 도메인을 고르면 그 도메인의 표가 만들어진다 (도메인당 1개)<br>AC2: 그 도메인의 현재 버전이 기준 버전으로 기록된다 | 초안 |
| SP-F02 | 기능 행 추가·수정 | 요구사항을 적는다 | AC1: 행은 ID, 기능, 목적, 수용 기준, 상태를 가진다<br>AC2: ID는 `도메인코드-F번호`로 자동 부여되고 바뀌지 않는다<br>AC3: 수용 기준은 1개 이상이어야 활성으로 바꿀 수 있다 | 초안 |
| SP-F03 | 수용 기준 ID | 테스트가 요구사항을 가리킬 수 있게 한다 | AC1: AC는 `기능ID-AC번호`로 자동 부여된다<br>AC2: 삭제된 AC 번호는 재사용되지 않는다 | 초안 |
| SP-F04 | 변경 기록 | 무엇이 바뀌었는지 행 단위로 남긴다 | AC1: 활성 행을 고쳐 저장하면 변경 크기와 요약을 입력해야 한다<br>AC2: 표 버전이 1 오르고, 변경 내역에 바뀐 기능 ID·AC ID가 기록된다<br>AC3: 초안 행은 기록 없이 자유롭게 고칠 수 있다 | 초안 |
| SP-F05 | 기준 도메인 재확인 | 도메인이 바뀌어도 표가 유효함을 확인한다 | AC1: 내용은 그대로 두고 기준 버전만 현재 도메인 버전으로 올린다<br>AC2: 재확인 날짜와 사유가 기록된다 | 초안 |
| SP-F06 | 낡음 표시 | 도메인과 어긋난 명세를 드러낸다 | AC1: 기준 버전 이후 도메인에 큰 변경이 있으면 표에 낡음이 표시된다<br>AC2: 작은 변경만 있었으면 표시되지 않는다<br>AC3: 어떤 변경 때문인지 함께 표시된다 | 초안 |
| SP-F07 | 검증 상태 열 | 요구사항이 실제로 지켜지는지 표에서 바로 본다 | AC1: 각 AC 옆에 통과 / 실패 / 테스트 없음이 표시된다 (Verification 결과)<br>AC2: 테스트 결과가 없으면 "미실행"으로 표시된다 | 초안 |

## 규칙

- 표는 구현 방법을 담지 않는다. 구현 방법은 Design에 둔다.
- 새 개념이 필요하면 Domain Modeling에 먼저 추가한다.
- 일정·기간은 적지 않는다.

## 미결정 사항

- 기능 하나가 여러 도메인에 걸칠 때 어느 도메인 표에 둘지 (주 도메인 하나에 두고 다른 도메인은 링크로 참조하는 안)
