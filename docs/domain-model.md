# Girsktop 도메인 모델

> 이 문서는 **전체 지도**다. 도메인 목록, 도메인 간 관계, 결정 사항만 둔다. 각 도메인의 역할·요구사항·설계는 `domains/<도메인>/` 폴더 안에 있다.

## 1. 배경

GitHub Releases로 배포하는 데스크톱 앱. 프로젝트의 도메인 모델, 기능 명세, 설계, 테스트, 나중에 할 일, 지식을 관리한다. 앱 안 터미널에서 Claude Code / Codex로 작업하고, 그 대화를 읽어 도메인 모델과 비교할 수 있게 한다.

해결할 문제 (opensmith에서 겪은 것):

| # | 문제 |
|---|---|
| P1 | 도메인과 기능 명세서의 버전이 따로 놀아 서로 어긋난다 |
| P2 | 나중에 할 일을 기록하지 못하거나, 시기·유형이 분류되지 않아 잊힌다 |
| P3 | 작업 대화에서 생긴 도메인 로직이 도메인 모델에 늦게 반영된다 |
| P4 | 요구사항이 실제 코드에서 지켜지는지 확인할 방법이 없다 |

## 2. 원칙

1. **도메인 하나 = 바운디드 컨텍스트 하나 = 모델 하나.** 하나의 모델로 여러 하위 도메인을 표현하지 않는다. 경계는 용어로 나눈다. 같은 단어라도 컨텍스트가 다르면 다른 개념이다.
2. **하위 도메인의 상위는 하나다.** 이름이 같아도 상위가 다르면 다른 도메인이다. 식별은 이름이 아니라 고유 id로 한다.
3. **도메인은 그래프로 본다.** 계층(상위–하위) 위에 의존·이벤트·참조 관계가 얽힌다. 계층을 폴더 중첩으로 표현하지 않는다.
4. **기능이 없는 도메인은 만들지 않는다.** 하위 도메인을 묶기만 하는 껍데기 도메인은 두지 않는다. 상위 도메인도 자기 기능이 있어야 한다.
5. **문서는 자동으로 고쳐지지 않는다.** 한쪽이 바뀌면 관련된 쪽에 "확인 필요"를 표시하고, 판단은 사람이 한다.
6. **도메인 이름은 다루는 대상을 가리키는 명사로 짓는다.** "할 일", "변경 검토"처럼 이름만 보고 무엇을 다루는지 바로 떠올릴 수 있게 한다. 영어 개념어나 추상적인 단어는 쓰지 않는다.
7. **도메인 문서는 자기 역할만 적고, 도메인 사이 관계는 이 문서 한 곳에만 둔다.** 각 도메인 문서에 관계를 적으면 남의 역할까지 설명하게 되어 역할이 섞이고, 관계 하나가 바뀔 때 여러 문서를 함께 고쳐야 해서 서로 어긋난다.
8. **기술 기능은 업무 도메인과 섞지 않는다.** 화면·알림·외부 연결 같은 기술 기능도 같은 4층 구조(역할 → 기능 명세 → 설계 → 테스트)로 만들되, 상위 도메인 **앱 기반** 아래에 모은다.

## 3. 문서 구조

### 4층

| 층 | 질문 | 담는 것 | 위치 |
|---|---|---|---|
| 1. 도메인 | 누가 무엇을 책임지나 | 역할, 경계, 용어 | `domains/<도메인>/domain.md` |
| 2. 기능 명세 | 무엇이 되어야 하나 | 요구사항 + 수용 기준(AC) | `domains/<도메인>/spec.md` |
| 3. 설계 | 어떻게 만드나 | 기능별 설계 / 시스템 공통 설계 | `domains/<도메인>/design/<기능ID>.md` / `system-design.md` |
| 4. 검증 | 실제로 되는가 | 테스트 | 저장소의 테스트 코드 (AC ID로 연결) |

**연결 규칙은 하나다.** 아래 층은 위 층의 버전을 기준으로 삼고, 위 층에 큰 변경이 생기면 그것을 기준으로 한 아래 층에 변경 검토를 띄운다.

### 배치

```
docs/
  domain-model.md        전체 지도 (이 문서)
  system-design.md       시스템 공통 설계
  domains/
    <도메인>/             도메인 하나 = 폴더 하나 (중첩 없음)
      domain.md          1층
      spec.md            2층
      design/            3층 (필요한 기능만)
```

### 작성 규칙

- **domain.md 섹션**: 역할 / 용어 / 하지 않는 것 / 문서
  - 다른 도메인의 이름을 쓰지 않는다. "하지 않는 것"에도 누가 대신 하는지는 적지 않는다.
  - 용어는 이 도메인 안에서의 뜻만 적는다. 같은 단어를 다른 도메인과 비교하는 일은 앱의 용어 검색이 한다.
  - 프로젝트 전반 용어는 Knowledge에 둔다.
- **기능 명세 표 열**: `ID | 기능 | 목적 | 수용 기준 | 상태`
  - ID는 `도메인코드-F번호`, AC는 `기능ID-AC번호`. 한 번 정하면 바꾸지 않는다.
  - 수용 기준은 테스트로 확인할 수 있게 쓴다.
  - 일정·기간은 적지 않는다 (Task가 맡음).
- **기능별 설계**: frontmatter `basedOn`에 기준 기능 ID와 표 버전을, 공통 설계를 참조하면 `refs`에 섹션을 적는다. 두 설계 이상에 반복되는 내용은 공통 설계로 옮긴다.

## 4. 도메인 목록

이름은 그 도메인이 **다루는 대상**을 가리키는 명사로 짓는다 (원칙 6). 폴더와 id는 처음 정한 영문 그대로 둔다.

| 코드 | 도메인 | 상위 | 유형 | 다루는 대상 | 해결 문제 | 폴더 |
|---|---|---|---|---|---|---|
| DM | [도메인](domains/domain-modeling/domain.md) | - | Core | 도메인·하위 도메인·개념·용어, 버전 (1층) | P1 | `domain-modeling` |
| SP | [기능 명세](domains/spec/domain.md) | 도메인 | Core | 기능 명세 표, 수용 기준 (2층) | P1 | `spec` |
| DS | [설계](domains/design/domain.md) | 도메인 | Core | 기능별 설계, 시스템 공통 설계 (3층) | P1 | `design` |
| VR | [테스트](domains/verification/domain.md) | 도메인 | Core | AC–테스트 연결, 실행 결과 (4층) | P4 | `verification` |
| IR | [변경 검토](domains/impact-review/domain.md) | 도메인 | Core | 변경에 대해 결정할 것: 변경 요청(바깥 → 도메인)과 확인할 문서(도메인 → 아래) | P1 | `impact-review` |
| DR | [도메인 점검](domains/drift/domain.md) | 도메인 | Core | AI가 지난 점검 이후 작업과 도메인을 비교해 제안, 사람이 판단 (바깥 → 도메인) | P3 | `drift` |
| TK | [할 일](domains/task/domain.md) | - | Core | Inbox, Task, 시기, 리마인드 | P2 | `task` |
| KN | [지식](domains/knowledge/domain.md) | - | Supporting | 결정, 프로젝트 용어, 컨벤션, 교훈 | - | `knowledge` |
| PL | [앱 기반](domains/platform/domain.md) | - | Supporting | 화면 이동, 알림, 빠른 기록 단축키, 자동 업데이트 | - | `platform` |
| WS | [프로젝트](domains/workspace/domain.md) | 앱 기반 | Supporting | 저장소, 데이터 폴더, 설정, 외부 변경 감지 | - | `workspace` |
| KG | [관계도](domains/knowledge-graph/domain.md) | 앱 기반 | Supporting | 문서 노드와 링크 | P1 (보조) | `knowledge-graph` |
| IN | [연동](domains/integration/domain.md) | 앱 기반 | Generic | GitHub, 세션 기록, 테스트 실행기, 내장 터미널 | - | `integration` |

업무 도메인(위 8개: 도메인과 하위 5개, 할 일, 지식)과 기술 기능(앱 기반 아래)을 섞지 않는다 (원칙 8).

## 5. 도메인 맵

도메인 문서를 최신으로 유지하는 흐름은 **방향이 반대인 두 가지**다.

```
 ┌──────────────────────────────────────────────────────────┐
 │ 도메인 (역할·용어·버전)                                     │
 │                                                          │
 │   ① 바깥 → 도메인                                          │
 │   도메인 점검 ──▶ 변경 검토(변경 요청) ──▶ 도메인 (사람이 반영) │
 │                                                          │
 │   ② 도메인 → 아래                                          │
 │   도메인 ─기준─ 기능 명세 ─기준─ 설계                          │
 │                   │                                      │
 │                   └─검증─ 테스트                           │
 │   위 층 큰 변경 ──▶ 변경 검토(확인할 문서)                      │
 └───────────────┬──────────────────────────────────────────┘
                 │ 보류된 확인, 빠진 테스트, 대화 속 할 일
                 ▼
            ┌────────┐      ┌──────┐
            │ 할 일   │      │ 지식  │ ◀── 도메인 점검에서 표시한 지식
            └────────┘      └──────┘

 ──────────────────────────────────────────────────────────────
 앱 기반 (화면 이동 · 알림 · 단축키 · 업데이트)
   ├ 프로젝트   열기·설정·파일 감지
   ├ 관계도     문서 링크 보기
   └ 연동       GitHub · 세션 기록 · 테스트 실행기 · 내장 터미널
```

## 6. 도메인 간 관계

도메인 사이 관계는 **여기에만** 적는다 (원칙 7). 각 `domain.md`에는 적지 않는다.

| 출발 | 도착 | 관계 |
|---|---|---|
| 기능 명세 | 도메인 | 기능 명세 표는 도메인 버전을 기준으로 삼는다 |
| 설계 | 기능 명세 | 기능별 설계는 기능의 표 버전을 기준으로 삼는다 |
| 설계 (기능별) | 설계 (공통) | 기능별 설계는 시스템 공통 설계를 참조한다 |
| 테스트 | 기능 명세 | 테스트는 AC ID로 수용 기준에 연결된다 |
| 도메인 · 기능 명세 · 설계 | 변경 검토 | 큰 변경이 생기면 아래 층 영향 검토를 시작한다 |
| 변경 검토 | 기능 명세 · 설계 · 테스트 | 영향받는 문서·테스트에 확인을 요청한다 |
| 변경 검토 · 테스트 · 도메인 점검 | 할 일 | 보류된 확인, 빠진 테스트·실패, 대화 속 할 일을 Task로 넘긴다 |
| 도메인 점검 | 지식 | 대화에서 표시한 지식을 초안으로 넘긴다 |
| 도메인 점검 · 할 일 | 변경 검토 | 도메인을 고치자는 변경 요청을 넘긴다 |
| 변경 검토 | 도메인 | 받아들인 변경 요청은 사람이 도메인 문서에 반영한다 |
| 연동 | 도메인 점검 · 테스트 | 세션 기록, 테스트 실행 결과를 가져온다 |
| 할 일 | 연동 | GitHub Issue와 동기화한다 |
| 프로젝트 | 관계도 | 앱 밖에서 파일이 바뀌면 관계를 다시 읽게 한다 |
| 앱 기반 | 할 일 · 변경 검토 · 도메인 점검 | 시기 도래, 남은 확인, 검토 주기를 알림으로 알린다 |

## 7. 결정 사항

| # | 항목 | 결정 |
|---|---|---|
| D1 | 문서 저장 방식 | **md 파일** |
| D2 | 버전을 매기는 단위 | **혼합.** 버전은 문서 단위(정수)로 매기고, 변경마다 변경 내역과 변경 크기(큰 변경 / 작은 변경)를 남긴다. 큰 변경일 때만 아래 층에 변경 검토를 띄운다. 기능 명세 표는 변경 내역에 바뀐 기능·AC ID를 남겨, 그 기능·AC를 기준으로 한 설계·테스트에만 변경 검토를 띄운다 |
| D3 | 도메인 점검 판단 주체 | **점검은 AI, 반영은 사람.** 지난 점검 이후의 작업 대화·커밋과 도메인 문서를 Claude Code·Codex에게 주고 맞지 않는 곳을 찾게 한다. AI는 근거와 함께 제안만 하고, 사람이 항목마다 받아들이거나 무시한다 |
| D4 | 사용 범위 | **1인** (팀 공유는 이후 검토) |
| D5 | 문서 층 구조 | **4층**: 도메인(역할) → 기능 명세 표(요구사항) → 설계(기능별 + 시스템 공통) → 검증(테스트) |
| D6 | 테스트 연결 방식 | 테스트 이름에 AC ID를 적는다 (예: `[PAY-F02-AC1] ...`). 결과는 JUnit XML로 읽는다 |
| D7 | 문서 배치 | **도메인 폴더 단위.** 도메인 하나의 1~3층 문서를 한 폴더에 둔다. 폴더는 중첩하지 않고 상위는 `parent`로 표기한다. |
| D8 | 에이전트 지침(하네스) | **두지 않는다.** CLAUDE.md·AGENTS.md 생성 기능은 쓰임새가 분명하지 않아 제거 |
