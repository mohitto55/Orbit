# Girsktop 도메인 모델

> 이 문서는 **전체 지도**다. 도메인 목록, 도메인 간 관계, 결정 사항만 둔다. 각 도메인의 역할·요구사항·설계는 `domains/<도메인>/` 폴더 안에 있다.

## 1. 배경

GitHub Releases로 배포하는 데스크톱 앱. 프로젝트의 도메인 모델, 기능 명세, 설계, 테스트, 나중에 할 일, 지식을 관리하고 이를 바탕으로 Claude Code / Codex용 Harness를 만든다.

해결할 문제 (opensmith에서 겪은 것):

| # | 문제 |
|---|---|
| P1 | 도메인과 기능 명세서의 버전이 따로 놀아 서로 어긋난다 |
| P2 | 나중에 할 일을 기록하지 못하거나, 시기·유형이 분류되지 않아 잊힌다 |
| P3 | 작업 대화에서 생긴 도메인 로직이 도메인 모델에 늦게 반영된다 |
| P4 | 요구사항이 실제 코드에서 지켜지는지 확인할 방법이 없다 |

## 2. 원칙

1. **도메인 하나 = 바운디드 컨텍스트 하나 = 모델 하나.** 하나의 모델로 여러 하위 도메인을 표현하지 않는다. 경계는 용어로 나눈다. 같은 단어라도 컨텍스트가 다르면 다른 개념이다.
2. **하위 도메인의 상위는 하나다.** 이름이 같아도 상위가 다르면 다른 도메인이다. 식별은 이름이 아니라 고유 id로 한다.
3. **도메인은 그래프로 본다.** 계층(상위–하위) 위에 의존·이벤트·참조 관계가 얽힌다. 계층을 폴더 중첩으로 표현하지 않는다.
4. **기능이 없는 도메인은 만들지 않는다.** 하위 도메인을 묶기만 하는 껍데기 도메인은 두지 않는다.
5. **문서는 자동으로 고쳐지지 않는다.** 한쪽이 바뀌면 관련된 쪽에 "확인 필요"를 표시하고, 판단은 사람이 한다.

## 3. 문서 구조

### 4층

| 층 | 질문 | 담는 것 | 위치 |
|---|---|---|---|
| 1. 도메인 | 누가 무엇을 책임지나 | 역할, 경계, 용어 | `domains/<도메인>/domain.md` |
| 2. 기능 명세 | 무엇이 되어야 하나 | 요구사항 + 수용 기준(AC) | `domains/<도메인>/spec.md` |
| 3. 설계 | 어떻게 만드나 | 기능별 설계 / 시스템 공통 설계 | `domains/<도메인>/design/<기능ID>.md` / `system-design.md` |
| 4. 검증 | 실제로 되는가 | 테스트 | 저장소의 테스트 코드 (AC ID로 연결) |

**연결 규칙은 하나다.** 아래 층은 위 층의 버전을 기준으로 삼고, 위 층에 큰 변경이 생기면 그것을 기준으로 한 아래 층에 확인표시를 띄운다.

### 배치

```
docs/
  domain-model.md        전체 지도 (이 문서)
  system-design.md       시스템 공통 설계
  domains/
    <도메인>/             도메인 하나 = 폴더 하나 (중첩 없음)
      domain.md          1층
      spec.md            2층
      design/            3층 (필요한 기능만)
```

### 작성 규칙

- **domain.md 섹션**: 역할 / 용어 / 하지 않는 것 / 다른 도메인과의 관계 / 문서
  - 용어는 이 도메인 안에서의 뜻만 적는다. 다른 도메인과 뜻이 다르면 비고에 적는다.
  - 프로젝트 전반 용어는 Knowledge에 둔다.
- **기능 명세 표 열**: `ID | 기능 | 목적 | 수용 기준 | 상태`
  - ID는 `도메인코드-F번호`, AC는 `기능ID-AC번호`. 한 번 정하면 바꾸지 않는다.
  - 수용 기준은 테스트로 확인할 수 있게 쓴다.
  - 일정·기간은 적지 않는다 (Task가 맡음).
- **기능별 설계**: frontmatter `basedOn`에 기준 기능 ID와 표 버전을, 공통 설계를 참조하면 `refs`에 섹션을 적는다. 두 설계 이상에 반복되는 내용은 공통 설계로 옮긴다.

## 6. 도메인 간 관계

| 출발 | 도착 | 관계 |
|---|---|---|
| Spec | Domain Modeling | 기능 명세 표는 도메인 버전을 기준으로 삼는다 |
| Design | Spec | 기능별 설계는 기능의 표 버전을 기준으로 삼는다 |
| Design (기능별) | Design (공통) | 기능별 설계는 시스템 공통 설계를 참조한다 |
| Verification | Spec | 테스트는 AC ID로 수용 기준에 연결된다 |
| Domain Modeling · Spec · Design | Impact Review | 큰 변경이 생기면 아래 층 영향 검토를 시작한다 |
| Impact Review | Spec · Design · Verification | 영향받는 문서·테스트에 확인을 요청한다 |
| Impact Review · Verification · Drift | Task | 보류된 확인, 빠진 테스트·실패, 대화 속 할 일을 Task로 넘긴다 |
| Integration | Drift · Verification | 작업 대화, 테스트 실행 결과를 가져온다 |
| Drift · Task | Domain Modeling | 사람이 수정하기로 한 내용을 도메인 변경으로 넘긴다 |
| Domain Modeling · Spec · Design · Knowledge | Harness | 원본이 바뀌면 하네스 재생성이 필요하다 |
| Task · Harness | Integration | Issue 동기화, 하네스 파일 쓰기 |

## 7. 결정 사항

| # | 항목 | 결정 |
|---|---|---|
| D1 | 문서 저장 방식 | **md 파일** |
| D2 | 버전을 매기는 단위 | **혼합.** 버전은 문서 단위(정수)로 매기고, 변경마다 변경 내역과 변경 크기(큰 변경 / 작은 변경)를 남긴다. 큰 변경일 때만 아래 층에 확인표시를 띄운다. 기능 명세 표는 변경 내역에 바뀐 기능·AC ID를 남겨, 그 기능·AC를 기준으로 한 설계·테스트에만 확인표시를 띄운다 |
| D3 | Drift 판단 주체 | **사람.** 앱은 주기적으로 검토를 요청하고 비교할 자료를 보여주며, 수정 여부는 사람이 판단한다 |
| D4 | 사용 범위 | **1인** (팀 공유는 이후 검토) |
| D5 | 문서 층 구조 | **4층**: 도메인(역할) → 기능 명세 표(요구사항) → 설계(기능별 + 시스템 공통) → 검증(테스트) |
| D6 | 테스트 연결 방식 | 테스트 이름에 AC ID를 적는다 (예: `[PAY-F02-AC1] ...`). 결과는 JUnit XML로 읽는다 |
| D7 | 문서 배치 | **도메인 폴더 단위.** 도메인 하나의 1~3층 문서를 한 폴더에 둔다. 폴더는 중첩하지 않고 상위는 `parent`로 표기한다 |
